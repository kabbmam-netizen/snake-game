# 贪吃蛇 + Supabase 排行榜：数据表设计分析

## 一、先把需求拆成三件事

| 需求 | 本质 | 谁来负责 |
| --- | --- | --- |
| 用户登录 | 账号、密码、会话 | **不要自己建表**，交给 Supabase Auth |
| 排行榜按用户名/邮箱显示 | 用户要有一份「对外展示的资料」 | 自建 `profiles` |
| 记录排名 | 要存「每一局」的成绩，才能算最高分/次数 | 自建 `scores` |

关键判断：**登录这件事不要自己造表**。Supabase 内置 `auth.users`，密码哈希、邮箱验证、JWT 签发全帮你做好了。自己存密码是安全事故的高发区。

## 二、需要建的表

### 表 1：`profiles` —— 用户资料

和 `auth.users` **一对一**。为什么不直接在 `auth.users` 上加字段？因为 `auth` 是 Supabase 管的 schema，你不该去改它；而且 anon 角色读不到它，排行榜就没法显示名字。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | uuid | PK，FK → `auth.users(id)` ON DELETE CASCADE | 与账号同一个 id，天然一对一 |
| `username` | text | NOT NULL, UNIQUE, 长度 2–20 | 排行榜显示的名字 |
| `email` | text | NOT NULL | **冗余副本**，见下方说明 |
| `avatar_url` | text | 可空 | 头像，可选 |
| `created_at` | timestamptz | NOT NULL DEFAULT now() | 注册时间 |
| `updated_at` | timestamptz | NOT NULL DEFAULT now() | 改资料时由触发器自动更新 |

> **为什么要把 email 冗余存一份？**
> `auth.users` 表只有 service_role 能读，前端用 anon key 查不到。而需求要求「按邮箱显示排名」，所以必须在自己的表里留一份副本。这是有意的反范式设计，不是偷懒。

### 表 2：`scores` —— 每局成绩

和 `profiles` **一对多**，一行一局。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | uuid | PK DEFAULT gen_random_uuid() | 主键 |
| `user_id` | uuid | NOT NULL，FK → `profiles(id)` ON DELETE CASCADE | 谁的成绩 |
| `score` | integer | NOT NULL, CHECK (score >= 0) | 本局得分 |
| `duration_ms` | integer | NOT NULL DEFAULT 0, CHECK >= 0 | 本局时长，反作弊参考 |
| `created_at` | timestamptz | NOT NULL DEFAULT now() | 何时打的 |

> **为什么不直接在 profiles 上存一个 `best_score`？**
> 那样只能看到最高分，看不到「打了几局」「什么时候打的」「进步曲线」。一行一局是更通用的建模，最高分用聚合算出来即可。如果后面要加「最近 10 局」「每日榜」，这个结构不用改。

### 对象 3：`leaderboard` —— 视图（不是表）

排行榜不是"存"出来的，是"算"出来的：

```sql
select row_number() over (order by best_score desc) as rank,
       user_id, username, email, best_score, games_played, last_played_at
from (
  select p.id, p.username, p.email,
         max(s.score) as best_score,
         count(s.id) as games_played,
         max(s.created_at) as last_played_at
  from profiles p join scores s on s.user_id = p.id
  group by p.id, p.username, p.email
) t;
```

好处：数据永远实时，不会出现"缓存分数没更新"的 bug。前端一句 `from('leaderboard').select('*')` 就能拿到排好序的结果。

```

    │ 1
    │
    │ 1
profiles ──────< scores
   id              user_id
 username          score
 email             duration_ms
                   created_at
    │
    └──> leaderboard（视图：每人 max(score) + rank）
```

## 四、必须配的 RLS 策略

| 表 | 操作 | 策略 |
| --- | --- | --- |
| profiles | SELECT | `true` —— 所有人都能看（排行榜要显示名字） |
| profiles | UPDATE | `auth.uid() = id` —— 只能改自己 |
| scores | SELECT | `true` —— 公开可读 |
| scores | INSERT | `auth.uid() = user_id` —— 只能以自己的身份提交 |
| scores | DELETE | `auth.uid() = user_id` —— 只能删自己的 |

**最容易漏的一条**是 `scores` 的 INSERT 策略。如果不写，登录用户能伪造别人的 `user_id` 提交成绩。

## 五、索引

| 索引 | 原因 |
| --- | --- |
| `scores(score desc)` | 排行榜按分数倒序，没有索引会全表扫 |
| `scores(user_id)` | 查"我的成绩"、算每人最高分 |
| `profiles(username)` unique | 唯一约束自带索引，重名检查走它 |

## 六、这套设计的边界（生产环境该补什么）

1. **分数可伪造**：现在分数由前端算完直接写库，改个 JS 就能刷榜。生产环境应该用 Edge Function 在服务端校验（比如限制"分数/时长"的合理区间，或服务端回放）。
2. **邮箱公开**：需求要求显示邮箱，但那等于把用户邮箱暴露给所有人。真实产品通常只显示用户名，或做打码（`ab***@gmail.com`）。
3. **没有分页**：现在取前 20 名够用，用户多了要加 `range()` 分页。
4. **没有时间维度**：想加"日榜/周榜"，在 `scores` 上加 `created_at` 的索引按时间过滤即可，表结构不用动。
